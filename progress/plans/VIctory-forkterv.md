# VIctory forks and an integration plan for the RX 9070 XT

26 November 2026 • Windows x64 • Radeon RX 9070 XT 16 GB • Core i5-14600KF • the stated 35 GB DDR5

(The first plan. The bundle based on Belobug's `rx9070xt` branch later became the playable base, see [PROGRESS.md](../../PROGRESS.md).)

**I would start the common release from PastiiJay/klbf-lab's `beta-2` branch, and use Victory United as a parallel control.** KLBF's advantage is documented play on the same GPU and a similar memory budget. Victory United's advantage is that for many other forks' changes it gives the original author, PR, adopting commit and the conflict. After the first local comparison we can decide which tree actually needs less fixing. [KLBF starting branch](https://github.com/PastiiJay/klbf-lab/tree/beta-2) · [Victory United provenance list](https://github.com/Fayberr/Victory-United/blob/main/PROVENANCE.md)

In KLBF's **Lab 61** measurement a 37-minute run with walking and driving averaged 14.0 fps, median 14.5, 1% low 0.4. They used a Series S + FSR 4 profile, a 9800X3D and 32 GB of RAM. **Lab 62** introduces new texture caps. Victory United measured the `3588725d` merge on an RTX 3080 Ti with 64 GB of RAM. Because of the different GPU, route and measurement window, no relative speed on your machine can be computed from these. [KLBF measurement and version](https://raw.githubusercontent.com/PastiiJay/klbf-lab/beta-2/README.md) · [Victory United measurement log](https://github.com/Fayberr/Victory-United/blob/main/docs/measurements.md)

## Suggested adoption order

| Order | Original idea and traceable change | What to check on the 9070 XT? |
|---|---|---|
| 1 | **Shared texture uploads.** AnyXboxX #304, `c650c225` in Victory United. Several heap views of the same content can share the upload. [Original PR](https://github.com/LooperSalty/AnyXboxX/pull/304) · [Adoption](https://github.com/Fayberr/Victory-United/blob/main/PROVENANCE.md) | First look for functionally equivalent code in the pinned KLBF version. If it is missing, test it as a single change. On the same car route measure the uploaded bytes, the long stops and the textures that appear late. |
| 2 | **Processing changed descriptors.** Flamingo `80001f1e` in VU's adoption. The periodic full check and the switch for the old full scan stay. [Adoption note](https://github.com/Fayberr/Victory-United/blob/main/PROVENANCE.md) · [Flamingo](https://github.com/realblastex/flamingo) | KLBF already uses `PORT_DESCRIPTORS`. It is only worth something for the needless walks still done. In A/B: CPU preparation time, faulty surfaces and missed draws. |
| 3 | **Less copy-back and CPU load.** 7900XTX `3ead56e1` in VU, with changed 4 KiB parts only. `VICTORY_PORT_CBV` and `VICTORY_PORT_GUARD` are separate experiments. [Adoptions](https://github.com/Fayberr/Victory-United/blob/main/PROVENANCE.md) · [7900XTX options](https://github.com/avatarmanz/VIctory-7900XTX) | Measure them separately first, then the winners together. A faulty copy may show sooner on a moving vehicle or animated clothes than with a still camera. |
| 4 | **Streaming and RAM.** KLBF Lab 62 documents the optional `VICTORY_TEXTURE_LRU`. ruff-lab's staging and worker handling, and Itsbatt/DexNom's per-range locking are two more, separate candidates. [KLBF](https://raw.githubusercontent.com/PastiiJay/klbf-lab/beta-2/README.md) · [ruff-lab](https://github.com/LoverCatys/ruff-lab) · [Itsbatt](https://github.com/Itsbatt/victory-unified) | Measure at 1024 and 512 px first, then with a single new memory feature. Record the private commit, VRAM, queued uploads and frames over 500 ms. |
| 5 | **Hybrid Intel CPU.** fxceless #1044 sizes the DirectStorage worker pool to the physical cores, with a manual override. This is a different thread pool from the `VICTORY_WIDE_THREADS=12` setting of KLBF's launcher. [Original PR](https://github.com/fxceless/victory-fork/pull/1044) · [KLBF launcher](https://raw.githubusercontent.com/PastiiJay/klbf-lab/beta-2/play.ps1) | During work measure decoding and render preparation separately. Change the thread pools one at a time. Let the result decide the worker count for the i5-14600KF. |
| 6 | **Shader correctness and lighting.** Belobug's helper-lane quad reads, Itsbatt's water shader outputs and BRVIctory/DexNom's RT path. Marvisak #1247 documents the separate effect of several shader packages. [Belobug](https://github.com/Belobug/VIctory-Belobug-AMD) · [Itsbatt](https://github.com/Itsbatt/victory-unified) · [BRVIctory](https://github.com/ka1qux/BRVIctory-ka1qux) · [Shader comparison](https://github.com/Marvisak/VIctory/issues/1247) | First the same interior, car glass, skin and water surface with the same exposure. RT should be a separate quality profile, with its own frame-time and memory results. |
| 7 | **Sound and control.** CHIMERA's XMA scheduling and ruff-lab's native PlayStation controller handling can be taken as separate features. [CHIMERA](https://github.com/LukaManstein/CHIMERA) · [ruff-lab](https://github.com/LoverCatys/ruff-lab) | Sound dropouts during shader compilation; connecting, unplugging and replugging a controller. They get higher priority if the fault shows in the local base version. |

## How the local comparison goes

1. Record both base branches' full git SHA, the driver version, the Xbox build, the Series S/X profile and the resolution. For the first comparison: KLBF Series S + FSR, no frame generation. Note it on the other tree if the same setting is not available.
2. Start from the same save, with a copy of its own for each tree. Use a short indoor walk, a busy car route and a waterfront stretch. Three warm-cache repeats are suggested, then a separate cold start. Each version builds its own cache in its own folder.
3. Record the whole run, the mean real fps, the p95/p99 frame time, stops over half a second, and the peaks of committed system memory and VRAM. KLBF's published 1% low comes from one-second fps samples. Put a per-frame p99 into a separate column. [KLBF method](https://github.com/PastiiJay/klbf-lab/blob/beta-2/docs/klbf/MEASUREMENT.md)
4. Compare the donor's SHA with the local base. With shared history `git merge-base --is-ancestor`, for a picked commit `git cherry` or `git patch-id --stable`, for a manual port comparing the actual function and test case gives a hold. Victory United documents a merge that marks an earlier state only in the history, so ancestry alone is not enough. [Victory United PROVENANCE.md](https://github.com/Fayberr/Victory-United/blob/main/PROVENANCE.md)
5. For each change note the original author, PR, donor and local SHA, licence, dependencies, switch, test and how to revert it. KLBF has a GPLv3 licence file. For the donors follow their own file headers and licences. [KLBF LICENSE](https://github.com/PastiiJay/klbf-lab/blob/beta-2/LICENSE)
6. What goes into the common base is what improves the target metric beyond the natural spread between runs, or fixes a reproducible picture, sound or stability fault. After an accepted fix, go back to the three scenes. To sum up speed-ups, only use the version run together.

## More sources and extending the list

- Victory United documentedly took code from the work of the since-removed `vitutu1/victory-perf`. `a37ac9a6` is especially instructive: by the provenance list it was later replaced by another implementation, although the commit is still part of the history. [Victory United provenance list](https://github.com/Fayberr/Victory-United/blob/main/PROVENANCE.md)
- A separate helper for uncovering shader regressions is Rafa23xz/victory-shader-census. For timing the renderer, avatarmanz's `crates/victory-gpu/src/replay` module replays even a single frame's GPU work. The donor notes that with a recording made in the world the game's watchdog may stop the run. [Shader census](https://github.com/Rafa23xz/victory-shader-census) · [Replay Rust source](https://raw.githubusercontent.com/avatarmanz/VIctory-7900XTX/main/crates/victory-gpu/src/replay/mod.rs) · [Replay documentation](https://github.com/avatarmanz/VIctory-7900XTX/blob/main/docs/replay.md)
- The accompanying **Forkhalozat.ps1** (local only) walks, in PowerShell 7, the public forks GitHub reports, recursively and with paging, starting from the table's repos. Usage from the folder of the two files: `./Forkhalozat.ps1`. The `victory-forkhalozat.json` created in the current folder holds the known repos and the pending queries. After hitting the API limit it can continue with the same command. Optionally an already set `GH_TOKEN` can be used. For a fresh survey give a new `-Snapshot` file name. The fork list identifies further candidates; their unique changes have to be examined separately.
