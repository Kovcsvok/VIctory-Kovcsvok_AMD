# Claude-32 – Lazy host lists: a submitted list gets a host list only when it is recorded again

Date: 2026-11-27, 17:30 (local time). Tree: `VIctory-dev\belobug-9070` (uncommitted, base cd8dfc06). The next RAM step for the 18 GiB working-set goal named in Claude-31 §5 and approved by the user.

## 1. What held the host lists (Claude-31 census, 16:47 run)

With `VICTORY_LANDED_EARLY`, 1,133 host lists were alive in gameplay: 144 idle in the pool, 286 held by the thin back lists nobody used (`thin::BACKS`), 16 in flights and **678 "other"**. At each submission `list::detach` took a list's host list and gave the list a new, closed one at once. With `VICTORY_THIN` that list is the back list of a title list's last recording, and it kept that host list until the title recorded the same list again. Every back list in `BACKS` kept one too.

## 2. What was built (`VICTORY_LIST_LAZY=1`)

- `list.rs::take_host`: with the switch, a submission takes the host list and leaves none. The list is marked `lent`.
- `list.rs::reset`: a `lent` list takes a host list from the idle pool, or a new one, at its next reset. Both are open for recording, so the extra close and reset per submission of the old path are gone. A second submission without a reset takes nothing and runs nothing, as the old path's empty closed list did.
- `list.rs::lend_empty`, called from `thin::Recording::run`: a recording of nothing (only its reset and its close, `inner.calls <= 2`, and `HostList::untouched`) gives its host list back to the pool at its close, before anyone may submit it. The title makes about 630 such lists at start-up; each held a host list until it was recorded again.
- **Soft pool cap** (`list.rs::to_pool`, `IDLE_KEEP` = 2 s): with the switch, lists past the idle cap (`VICTORY_LIST_IDLE_MOST=256`) are let go only once the oldest idle one has waited 2 s, with at most four times the cap. With a hard cap the first run let go of lists at landing and made new ones at the next resets (§3).
- Census line: `{backs} held by the {backs_all} lists of ours nobody uses`; the thin line adds `recordings of nothing whose host list went back`.
- Test `list::tests::a_submitted_list_holds_no_host_list_until_its_reset` (real host GPU, not skipped):
  - lazy take, none left, nothing taken a second time;
  - the reset takes an open list, which closes without failure;
  - `lend_empty`, then the reset after it;
  - the old path unchanged.
  - Passes, with the other list and thin tests.
- Launcher: `meres-csomag.ps1 -ListaLusta be|ki`, **default `be` since 17:25**, with `-ListaKorai be`.

What it shows:

- **Lists:** the lazy host list empties the thin backs (0 of 277 hold one). The empty-list step and the soft cap take the live lists down to 409, about a third of the baseline, and the menu to 265.
- **Churn:** run 1's hard cap of 256 let go of lists as flights landed and made new ones at the next resets. That was 5 to 15 a frame in some periods, up to 43 ms a frame of the threads making them. The soft cap removes it: 314 made in the second half instead of 7,854.
- **RAM:** the medians are about 1 GiB lower than the baseline in both runs (working set 17.8–18.0 instead of 18.95, private 23.2–23.6 instead of 24.3), and shared GPU memory is 0.8–1.0 GiB lower.
- **The peak varies with the run, not with the lists.** It comes in the first ~15 s after the world loads, about 2 min into each run:
  - 18.84 GiB in run 1;
  - 21.08 GiB in run 2, above 19.5 GiB for 15 samples;
  - 21.62 GiB at baseline, above 19.5 GiB for 83 samples.
  - Run 2 had half the lists of run 1 and the higher peak. At that moment private memory rose by ~2 GiB in every run (22.7 → 24.6 in run 2, 19.8 → 22.7 in run 1). That growth is the next target, not the lists.
- A possible reason run 2 is no lower than run 1 at the median: lists kept and reused keep their command allocators at the size of the largest recording they held, while run 1's churn made fresh, small ones. Not measured directly.

**Decision:** on by default (`-ListaLusta be`, every menu option), the version of run 2. The live lists fell from 1,133 to 409, the median memory is ~1 GiB lower, frames are not slower, and the churn is gone.
