## 2. The video was not closed; repaired

**What happened:** the game was closed with the window's close button. The program then ends with `TerminateProcess` and did not close the recording. The file lacked:
- its index (`mfra`);
- its duration.

Without them Windows does not open it (`Error creating clip from file`). All frames were there.

**Repair, in the file:**
- I appended the 68-byte index, the same one as in the working 10:52 video (its first fragment also starts at byte 748);
- I wrote the duration into the header: 8,766 frames, 292.2 s.

The picture data was not touched. To undo: cut the last 68 bytes and zero the duration (`mvhd`, 8 bytes from byte 123).

**Fix in the code:**
- `record.rs`: new `end_at_exit`. If the process ends during a recording, it closes the file the same way F9 does. It waits at most 3 s in all for the lock and the writer thread.
- `victory-hle` `lifecycle.rs`: the exit (`end`) calls it before `TerminateProcess`.

**Check:** a test start, recording from second 45, then the window closed with the same message as the close button.

## 7. The common suspect: lost GPU writes into compressed textures

**In the log, again:**

```
placed unordered texture view not mirrored (null: writes through it are lost)
```

| Time (UTC) | Lost writes so far | What the video shows |
|---|---|---|
| 10:32:35–36 | 1 → 1,024 | the scene loads |
| 10:32:40 | 2,048 | |
| **10:33:09** | **4,096** | **the woman with the garbage face (31–34 s = 10:33:07–10:33:10)** |
| 10:34:36 | 8,192 | 20 s before Cal's scene |

**Formats:** BC1 (71), BC1 sRGB (72), BC4 (80), BC7 (98); 32–1024 px, with full mip chains.

**What this means:**
- The game compresses some of its textures itself on the GPU and writes the finished compressed blocks into them.
- On PC, D3D12 does not allow a writable view of a compressed (BC) format, so our layer gives a null view and the writes are lost.
- The texture keeps whatever was in that memory before.

**It explains all three problems:**

| Problem | Explanation |
|---|---|
| garbage face | random bytes read as BC1 give colourful blocky noise |
| Cal's beard and moustache | the hair is a texture that carries transparency (BC4/BC1). Left at zero, the hair is fully transparent, that is, gone. Left with old content, it is patchy. |
| the tourist boat's side wall | the game makes the far, smaller levels itself. If they are empty, the wall is transparent at a distance, but present up close. |
| Lucia's eyebrows and eyelashes (probably) | the same kind of hair texture |

**This is still a hypothesis.** The proof will be the problems going away with the fix.

## 8. The plan for the fix

**The idea:** the card cannot write into the compressed texture. But:
- it can write into an uncompressed "block twin" of the same size, where each element is one block: 8 bytes for BC1 and BC4 (`R32G32_UINT`), 16 bytes for BC5 and BC7 (`R32G32B32A32_UINT`), a quarter as wide and as tall;
- D3D12 allows copies between a BC texture and an uncompressed format of the same block size.

So the game's writes go into the twin, and we copy from there into the real texture.

**What has to be found first:** which texture the game writes to, that is, the address.
- In the game's shader views the address is in words 10–11 of the description.
- In these writable views those words are 0.
- Until now only the first 10 words of the description were logged.

**So the new exe logs the full 16-word description**, for up to 64 different views. The test start stayed in the main menu (the account picker needs a controller), so they did not show up there yet. The user's next run will show them.

**Steps:**
1. The location of the address, from the next run's log.
2. The block twin and the copy, behind a switch (`VICTORY_BC_WRITES`) with live A/B, so one run shows the difference.
3. A test in the same scene: the garbage face, Cal's beard and the tourist boat.
