## 2. Try 1: keep the kept threads awake (`VICTORY_WIDE_SPIN`)

- The recordings show a submission's snapshot jobs and refreshes running one after another on one kept thread, with 2–3 ms a frame of "woken, not running yet" on the chain.
- `VICTORY_WIDE_SPIN` (default 0) keeps those threads spinning after a job. It was made live for the A/B: 300 µs when on.
- Run `20261127-232537-ebresztes-ab`: 12 min, unattended, the save loaded by `VICTORY_AUTO_A=25,100,5`, 30 s phases, from minute 3, no device error.

- Paired difference: **−0.05 ms**. No effect. The live switch was taken out again, and the comment on `spin` records the result.

## 3. Try 2: do the four late fills at the gate of `VICTORY_LATE_FILLS=2`

- Mode 2 opens a gate when the card has run the flights ahead, not when they have landed. Until now it kept learned fills that card steps would take to the card (those reading what flights declare writing) waiting.
- A new switch `VICTORY_LATE_CARD_FILLS=1` left those to the gate as well: the fill reads title memory, which holds the title's late write but not yet what the flights' shaders wrote.
- That is right only if the shaders do not really write those bytes. The landing's compare of fills done on the CPU checks that.
- Run `20261127-234340-keso-kartya-ab`: 12 min, unattended, `VICTORY_LATE_FILLS` live (0 against 2), from minute 3:

## 4. What this means

- The 16 ms a frame of waiting is a GPU → CPU → GPU round trip:
  - in-flight shaders write a buffer in a host copy;
  - the next submission's small fill reads it, together with bytes the title's CPU writes after sending;
  - so the fill waits until the flights have landed and title memory holds both.
- The user's friend's first two tips (keep GPU-only data on the GPU; track per region whether the CPU or the GPU holds the latest bytes and move only that) are exactly this case.
- Two ways forward:
  1. **Card copies for these buffers.** Existing switches: `VICTORY_CARD_BUFFERS_MIN_MB` (4 MiB by default on this 16 GB card), `VICTORY_CARD_BUFFERS_MIN_KB=64` (every title buffer on the card), `VICTORY_CARD_ALL`.
     - The log's own hint: "55.6 MB in copies of 1 MiB or more (VICTORY_CARD_BUFFERS_MIN_MB=1 would have the card look there)".
     - They are set at start, so it takes two runs, not a live A/B. The off phases of the two runs above differ by 3.8 ms at the same save (draws 7,076 against 4,439), so a run-to-run compare needs several runs.
  2. **For the four learned fills only:** when the card has run the flights ahead, take each dword from the host copy if the shaders wrote it (it differs from the snapshot), else from title memory (the title's late write). That is the landing's merge, but for 4 × ~0.5 KB instead of the whole range.
     - It is correct by construction, if the host copy is on the PC's side (not a card copy) and the snapshot is kept until then.
     - The fill's compare after landing (§3) measures it.
