## 3. Late constant buffers in place (`VICTORY_INPLACE_LATE_CBV`)

### 3.1 Port and fix

- `inplace.rs`: `register_late_cbv` opens the 64 KiB pages of a learned fill (private memory committed whole, not a view, at most 1,024 pages) with `place_part` (`OpenExistingHeapFromAddress1`); `late_cbv_part` gives a buffer and GPU address **only if the whole view lies in one opened page**; `forget_late_cbv_pages` from `title_memory_freeing`.
- `card_steps.rs::late::learn`: opens the pages, **and still learns them as before**. Antigravity's `learn_at` returned without learning, and `written_at` said "not written" for any range whose pages were all opened, while the binding takes only one page: a constant buffer over two opened pages lost its wait and was filled at submission (the bug GPT found).
- `draw.rs`: a table constant buffer in an opened page is pointed there (`constant_raw_at`, or `constant_at` on 256 bytes) and **gets no fill**; one that is not pointed there (over two pages, slot refused, or in mode 1 under flights' declared shader writes) keeps its fill, which the learned page makes wait as before. So the wait is left out exactly where the binding succeeded.
- Modes: `1` leaves ranges that flights in the air declared shader writes over to the fill (their writes reach title memory only when they land); `2` points those in place too (Antigravity's behaviour). Live A/B works (`VICTORY_AB=…,VICTORY_INPLACE_LATE_CBV`), unlike Antigravity's version.
- Test `inplace::tests::warp_late_constant_buffers_one_page_only_and_the_gpu_reads_late_bytes` (software adapter, write-watched memory): a buffer inside a page gets its place, the GPU reads the title's bytes there, **also bytes the CPU wrote after the place was given**; over the boundary of two opened pages, over into an unopened page and on an unopened page: no place. Passes, with the existing card-steps and in-place tests.

- It works: 5 pages opened, 140–230 slots a frame read in place (~200 KB a frame not filled), 9–41 of them under flights' declared writes (bound anyway in mode 2). No device error.
- **It does not remove the LEARN waits** (2.1–3.9 a frame either way) and gives no measurable gain (38.2 vs 38.6 ms at the same draw count). The waits come from **root** constant buffers: `draw.rs::root_view` fills those not on 256 bytes into scratch (`fill_scratch`, up to 64 KiB, the console needs only 16-byte alignment). Of the learned places 0x956fde850, 0x948a0fbb0, 0x99276ed80, 0x992738280, 0x95dacffd0, 0x977ebfa60 none is on 256 bytes, so a root view cannot point there.
- **Decision:** stays off by default.

## 4. RAM: landed lists given back at once (`VICTORY_LANDED_EARLY`)

### 4.1 What it does

- `host.rs::land`: with the switch, every landed flight's lists are recycled at once (`list.rs::recycle_early`), not after the last 64.
- `HostList::take_named` takes out what the list's commands named (deferred work and its kept objects, texture states, twins, scratch chunks, batch buffers), and with the detached upload memory and descriptor state it goes to `retire`, which drops it after the same `bury_lag` as before. The allocators (whose runs are over: the flight landed) are reset and the list goes to the idle pool. So **the retention of everything the commands named is unchanged**; only the list objects come back earlier.
- `VICTORY_LIST_IDLE_MOST=256` with it (the idle pool's cap; it was 512).
- Launcher: `meres-csomag.ps1 -ListaKorai be`.

The runs are not the same scene, so this is a direction, not an exact saving. No device error.

**But frames got slower** (25,000–30,000 list calls a frame: 49.3 ms against 40.8 and 46.2 in the two earlier runs): the thread that lands flights spent 29.6–33.8 ms a frame landing instead of 14.6–23. Cause: `bury` ran on that thread and now dropped the thousands of objects the landed lists named, which the helper thread used to drop in its reset. Fix: with the switch, `bury` hands them to `BURIED`, and the helper thread drops them in `land` (later, never earlier).

## 5. Toward 18 GiB: what is left

- The peak working set is now 21.6 GB: about 3.6 GB above 18.
- **Next list target: "other" (~620–860 lists).** At a title list's submission `list.rs::detach` gives the list a fresh host list at once; with `VICTORY_THIN` that is the title list's back list, which keeps it until the title records that list again. The title makes ~630 lists at start-up, many used rarely. Giving the back list its host list only when it records again (and the pool the rest) could save most of them. Not built yet.
- Thin `BACKS` (back lists nobody uses, each with its host list): 130–350. The same lazy host list would cover them.
- The windows' host copies (about 3.7 GB at the 11:31 peak) are the second target named by GPT; not touched here.
