### When does KLBF retry a refused GPU memory allocation?

**Right away, at the next texture, with no time-based hold-back.** This holds for the heap (`placement.rs` 144), the upload buffer (`host.rs` 8192) and the standalone texture (`resource.rs` 2942). In the `heap_textures` pass a failed upload counts 0 bytes (`draw.rs` 2335 `SPENT.fetch_add(bytes)`, where `bytes = 0`), so the byte budget (`draw.rs` 2176) does not run down. The pass only stops at the 250 ms time budget (`draw.rs` 2145; 1.5 s when catching up, 2155) or after at most 4,096 due slots (`draw.rs` 2099). So under memory shortage a single pass can make thousands of failing driver calls. The donor reproduced exactly this series: 8 uploads were 8 block-creation attempts in one pass.

There is one exception: if creating the GPU-side texture itself fails, `hosted` (`resource.rs` 1587) marks it permanently refused, and it is not tried again for that title texture until the game recreates the resource.

### What happens to waiting textures when Windows has little commit left?

1. **Nothing holds them back.** KLBF only watches VRAM. Upload buffers are allocated from the UPLOAD heap in system memory and load the commit limit. So there may be room in VRAM while commit has run out.
2. **On a failed upload the slot loses its retry.** If `stage_buffer` gets E_OUTOFMEMORY, no `STAGING` entry is made. `staged()` is then `None`, so the line falls back to `(0, true)`, and the slot becomes `done`. KLBF counts it with 0 MB in the "… uploaded so far" counter (`draw.rs` 2342) and schedules no re-check, since `staged_memory` is `None` (2330). The texture stays empty or old until the game rewrites the descriptor or remaps the memory. For materials picked by index (bindless) this was the only retry. Textures bound through a table try again at the next command list (`texture.rs` 692 `first_use`).
3. **Expected symptom:** a frame-time spike during the failing series, then lasting missing, black or blurry textures. KLBF's README also mentions that the game sometimes stutters when the GPU or system memory fills up, but does not name the cause.

**Portability:** KLBF lacks the donor's `pool.rs` and `residency.rs` infrastructure, and has `now_ms` instead of `coarse_ms` (`host.rs` 99). The smallest targeted port, in my view, has three parts: (1) a 500 ms hold-back after E_OUTOFMEMORY in the error branches of `Host::upload_buffer`, `host_texture_as` and `Heaps::allocate`; (2) after a failed staging, `heap_textures` should not call `texture_slot_done(…, None)`, but keep the slot due and leave the loop; (3) the 4/2 GiB commit gate only if measurement shows free commit below 4 GiB. I estimate 60–90 lines. **I made no change**, because the starting prompt's condition, that the code difference and the measurement point to the same fault, is not met yet.

  - `memoria.csv` comes every second from the new sampler.
  - **So no frame-time p95 can be computed.** PresentMon is not on the machine.
- **Warm-up.** A0 will be a cold run: the first play run after the pre-build finished at 14:36. The pipeline cache is pre-built; the run-time cache is empty.
