## 2. d1fa22a: `caf96a3229145fa6` and `VICTORY_DXR_OPT`

**What it does.** One switch, `VICTORY_DXR_OPT` (default on), turns on three things:
- In `lower.rs`, the post-loop hit metadata reuses one `COMMITTED_STATUS` pair per ray-query loop, instead of building a 5-block diamond for every read.
- In `opt.rs`, committed ray-query state reads are treated as pure when no `TraceRayInline`, `Proceed`, `Abort` or `Commit*` on the same handle is reachable. They are also kept across unrelated stores within a block.
- In `dxr.rs`, BLAS refit (`PERFORM_UPDATE`) becomes the default. In the donor it was off by default.

The switch is part of the translation fingerprint and of the shader-cache key.

**What was measured.** Static counts only, on one shader:
- `COMMITTED_STATUS` calls: 12 → 2;
- container size: 47,256 → 47,056 B (−200 B);
- validation errors: 0.

No GPU time was measured, and the game was not run with it.

**Assessment**
1. **The expected gain is small.** These queries run once per ray, after the traversal loop. The shader's 10.39 ms (donor figure) is spent in the BVH traversal and the any-hit passes. Those are unchanged: `rawBufferLoad` stays 132 and `CAND_BARY` stays 4. A gain on the order of a few percent of that shader, or less, would not surprise me. Only option 3 of its launcher (GPU timing) can tell.
2. **The A/B confounds two changes.** Option 4 (`VICTORY_DXR_OPT=0`) turns off both the shader change and the refit. Refit can make traces slower, because the BVH quality decays between the full rebuilds every 64 frames. It can also make them faster, because building is cheaper. An A/B should fix `VICTORY_NATIVE_RT_REFIT` explicitly on both sides; the code already lets an explicit value override.
3. **A correctness risk the validator cannot see (not shown to happen).** The cached status values in `lower.rs` are reused in any later block that the defining block dominates.
   - Suppose the ray-query loop sits inside an outer loop, for example several rays per invocation. A later iteration can then reach the reusing block without passing the defining block again.
   - The reusing block would then read the status of the previous ray.
   - In `opt.rs` the reachability check guards against this; in `lower.rs` only dominance does.
   - Image checks would catch it: the shadow of a moving character, reflections, foliage.
4. **The opt.rs rule looks sound.** A committed read counts as pure only if no mutator on the same handle comes later in its block or is reachable from it. The opcode list (184, 188, 189, 192, 194, 200, 207–212, 215) matches the DXIL committed-query opcodes.
   - It assumes one SSA handle per query. A handle passed through a phi would escape the mutator check.

## 3. 6a5c875: the port of the leak fix and the rest

**The descriptor port** carries the 353b50a entry ring (`oldest_loose`). Once the table holds `VICTORY_VIEW_ENTRIES_MAX` (262,144) entries, it reuses the next entry with no resource object, whatever its age. That includes samplers made at the start, and views used in the current frame, whose records then go stale.
- Claude-34 §4 did not take this ring for that reason.
- With buffer views encoded inline, the table may never fill in a normal session, so the risk is latent.
- If that tree is kept, the Claude-34 rule is safer: reuse only constant and placed views idle for 30 s.

**`Shadow::register` retire** (an old shadow is marked dead when a buffer is registered again at the same place): no objection.

**`VICTORY_WINDOW_BUDGET_MB=2048`** in `agy-dxr-profil.ps1`. In our 41-minute run the windows were flat at 2.8–4.1 GB (Claude-34). A budget below the working size forces unmapping and remapping, which shows up as hitches. I would leave it unset unless a run shows it helps.

**Tests.** The report says 4 victory-gpu and 3 victory-shader failures existed before. I did not check that against the base, because it needs a test run and the user was playing.

## 4. What is useful for us now

**Donor commit 7c90c19** ("lock-free shadow FOUND/seqlock, DenseRanges, fused list planning"; 7 files, +480/−120) is item 3 of `RT-30FPS-rangsor.md`.
- It aims at the update checks on the submitting thread. Those checks took 8.95 ms a frame in the 18:14 run, with 86 % of them finding nothing to copy.
- Our tree has none of it: `nothing_new_ranged`, `ranged_seq` and `DenseRanges` are absent from `watch.rs`, `shadow.rs` and `draw.rs`.
- If the long run confirms that the update checks and our submit chain take the time behind the idle card, this is the first donor code to port.

**Coordination.** Antigravity's `cargo test -j 12` (22:07) and its shader prewarm (173.8 s, 25,782 shaders) were heavy jobs on the same machine as our measurements. Heavy agent jobs should wait while the user plays or a measurement runs.
