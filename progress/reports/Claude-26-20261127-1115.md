## 4. New: garbage faces; the suspect is lost texture writes

**In the video (27–33 s):** the face of the woman holding the baby is covered in colourful, blocky "rainbow garbage". In the 10:22 run the policeman's face (6 s) looked the same.

**In the log:**

```
placed unordered texture view not mirrored (null: writes through it are lost)
```

The game writes on the GPU into compressed textures that it placed in memory itself:
- BC1 / BC1 sRGB, 256–1024 px;
- BC5, 1024 px;
- BC7.

Our layer does not follow these writes; it drops them (`descriptor/host.rs` 4613–4634: "shortcut"). The counter:

| Run | Lost writes | When |
|---|---|---|
| 10:52 | over 8,192 | passed it at 145 s |
| 10:22 | over 16,384 | |

They are dense at the start: 1,024 writes in 0.4 s at 09:53:32, which is the scene loading.

**Why this is the suspect:**
- If a GPU write is lost, the texture shows the previous contents of that memory. Random bytes read as BC1 give exactly this kind of blocky, colourful noise.
- Textures put together and compressed during play are typically faces (skin, make-up, stubble).
- Both garbage faces belong to minor characters and came right after a scene loaded.

**Ruled out: `VICTORY_TEXTURE_NO_WAIT`.** While the garbage face was on screen (09:53:50–09:54:12) every texture refresh was read in full: 0 deferred, 0 partial.

**Open question:** the logged views' address is `0x0`. Before a fix, we have to find out where the game really writes. Every local fork (avatarmanz, DexNom, cool_fox, klbf, Victory-United, Antigravity) drops these writes the same way; there is no ready fix.
