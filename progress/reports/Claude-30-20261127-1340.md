## 2. Automatic A (`VICTORY_AUTO_A`)

**Where:** `crates/victory-hle/src/modules/gameinput.rs` (module `auto_a`), hook in `xgamesave.rs`.

- The game's own stand-in pad (the one the keyboard and every host pad feed, `VICTORY_ONE_PAD` default) gets the A bit for 150 ms every 5 s, from 25 s to 150 s after the input object is made. To the game this is exactly a controller press. No driver, no system change, nothing outside the process.
- It stops for good when:
  - any input of a person's arrives (a pad button, trigger or stick, or a key held in the game's window), or
  - the game lists its saves after a press (= past the account picker), or
  - 150 s have passed.
- `VICTORY_AUTO_A=<from>,<until>,<every>` keeps pressing until `until` (for unattended test runs; it walks through the main menu).
- Log lines: `auto A: pressed n=…`, `auto A: the title lists its saves, past the account picker`, `auto A: a person's input`.

## 3. The 20 ms wait (`VICTORY_LATE_FILLS`)

### 3.1 The plan of Claude-29 did not fit

> **Correction (Claude-31, 16:40):** the claim below that the block cannot be used in place is wrong. `inplace.rs::place_part` already opens any 64 KiB part of private (also write-watched) memory with `OpenExistingHeapFromAddress1`, without pinning the whole allocation; Antigravity built the late-CBV path on it (agy-9070-v2 141b746). Claude-31 ports and measures it.

Claude-29 proposed that the card read the 13 learned pages in place, like renderer port 1. The pages are at 0x948a0f000–0x9939f2000: all in one 1,277 MB block of the title's (`XMemVirtualAlloc`, protection 0x2404, at 0x948a00000). The layer allocates that block with `VirtualAlloc2` + `MEM_WRITE_WATCH`, not as a section. Port 1 works only on section-backed 32-bit memory (a second view of the same section, opened as a heap). Opening this block directly would pin all 1.25 GB and conflict with write watching. So that plan was dropped.

### 3.2 What was built instead

New file `crates/victory-gpu/src/host/late_fills.rs`, hooks in `host.rs` (`submit`, late path) and `host/card_steps.rs` (`take_steps`).

- Before: a submission with a fill on a learned page was refused card steps and **the submitting thread waited** until the flights ahead had landed (3.6 submissions, 20 ms a frame at the boat), then did its fills.
- Now: the submission is sent at once, behind `ID3D12CommandQueue::Wait` on a fence of ours. A thread of ours (`victory-late-fills`) waits for the same moment (mode 1: the flights ahead have landed, `FINISHED`), reads those fills again from title memory into the submission's upload memory, and signals the fence. The card goes on; the submitting thread was free all along.
- Safety: only with `VICTORY_RELAY` and `VICTORY_RELAY_COPY=1` (otherwise a landing could wait behind the gated submission). A gate not opened in 2 s opens anyway (logged), so the card never waits on us for good. The landing check of LEARN (`found written again`) still runs on these fills.

### 3.3 First test: the gate never opened

In the 13:09 run every refused submission (2.3–3.6 a frame) still waited: the learned fills were among the fills **card steps take to the card** (they read memory flights ahead write), and the first build only deferred fills left to the CPU. `late fills … 0.00 submissions sent at once … 2.62 still waited`.

Second build: in mode 1 a learned fill taken to the card because it reads what flights ahead write is left to the CPU and done again by the gate thread (after they landed, title memory holds what they wrote). Only one that reads what a copy taken to the card writes still waits.

### 3.4 Second test (run `20261127-131705-kesotoltes-proba`, live A/B every 20 s, the user playing)

The gate now works (5.3–6.1 submissions a frame sent at once, ~200 fills done again, 38–88 of them changed since preparing, no gate timeout, no device error), but frames got **slower**:

| Phase | Late fills | Draws/frame | Mean ms | Card busy | Submitting thread waits |
|---|---|---|---|---|---|
| 4 | off | 1,386 | 33.5 | 45 % | 8.1 ms |
| 5 | on | 1,372 | 39.9 | 94 % | 22.1 ms |
| 6 | off | 1,363 | 35.9 | 41 % | 8.5 ms |

"Card busy" counts the queue holding our gated submission, so it is not real work. Each gate opens only after the flight ahead has landed (card done + relay copy-back), so the card idles through every landing; and more submissions are gated (5–6 a frame) than were refused before (2.3–2.7), because the learned set grew from 13 to 19 pages. The fills read memory the flights' shaders write (declared over the 1,277 MB block), so the dependency card → copy-back → title → card is real; moving the wait from the CPU to the card does not remove it.

**Decision:** `VICTORY_LATE_FILLS` stays off by default and is not in the menu. The real fix would be to keep that block on the card without copy-back (in place, as port 1 does for the 32-bit block), which needs it allocated as a section: a larger change for Codex to decide.
