# Claude-14 · The vanishing canopy: the bundle reads zeros where a texture was replaced

26 November 2026, 20:45 (local time). Previous: [Claude-13](Claude-13-20261126-2035.md); Codex's observation: [Hajos-part-villogas.md](Hajos-part-villogas.md), crop `Hajos-part-3m44.jpg` (local only).

## Starting point

- **The user:** trees and pillars appear and vanish as a whole, they do not just get their texture late.
- **Codex** showed it in the 3:44 stretch of the frame strip (`203210-881`, `203211-133`, `203211-384`, local time):
  - a large canopy vanishes within half a second, the sky shows in its place, then it comes back;
  - meanwhile the log shows 30.1 fps.
- Codex separated two possible causes:
  1. the draw command is left out as well;
  2. the draw runs, but the leaves' transparency mask is missing.

## What in the bundle's code and log points to case 2

**`crates/victory-gpu/src/descriptor/host.rs`, `keep_shown()`:** what should a texture slot show when the game overwrites it with another texture, until the new one has been made and uploaded?
- The code's own description: "`VICTORY_KEEP_SHOWN`): 0: never, it reads as zeros, then as the neutral texture; 1: one of the same kind in another place or size; 2: any of the same dimension".
- The default is **1**: it keeps showing the old one only if the new one is of the same kind (`Kin::Moved`/`Kin::Sized`).
- If the new one has the same dimension but is different (`Kin::Other`: another format or aspect ratio), the slot **reads zeros** until the new one is up.
- With zero alpha, a transparency-masked canopy vanishes entirely and comes back after the upload. That matches the 3:44 frame strip.

**The log at 19:32:1x UTC, in the same minute** (`slots that showed a texture and were written with another, since the start`):
- 252,190 "of the same kind elsewhere" and 436 "of another size": for these it keeps the old one;
- **47,905 "others": for these it does not**;
- 13.1 million "of another dimension": another dimension or not a texture; no setting keeps these;
- "252,626 of them kept what they showed meanwhile".

47,905 replacements not kept over the 12-minute run is about 66 a second. That is enough for the vegetation on the shore to flicker regularly.

**What this does not settle:**
- whether the 3:44 canopy went through exactly such a replacement;
- whether case 1 (a draw left out) plays a part as well.

The bundle's log gives no per-object identifier.

## The test

`VICTORY_KEEP_SHOWN=2` keeps showing the old texture on every replacement of the same dimension until the new one is up. No code change is needed.

**Risk:** for a few frames an old texture of another format may show in its place (wrong colour or pattern). The author may have left it at 1 for that reason. That fault is less striking than a vanishing object.

`Inditas-Csomag.cmd` (all 512 px + PC FSR):

| Option | Setting | Aim |
|---|---|---|
| `1` | `VICTORY_TEXTURE_LOOK_MS=250` + frame strip (3 a second) | the profile approved by Codex: textures popping in late |
| `2` | like `1` + `VICTORY_KEEP_SHOWN=2` + frame strip | vanishing canopies |
| `3` | the 20:20 setting | proven base |
| `4` | `-Safe` | spare |

`meres-csomag.ps1`'s new parameters: `-KeepShown`, `-Kepsor` ("kepsor" = frame strip). The frame strip goes into the run folder's `kepsor` subfolder and stops with the game. Both runs go on the same boat save, on the same shore, so the two strips can be compared.

*(Later, Claude-15: `KEEP_SHOWN=2` did not help; Claude-21 found the real cause, null twin views in the tree culling pass.)*

## The decision asked of Codex

**I ask Codex to approve the two runs one after the other on the same shore: `1`, then `2`.** Decision rule:
- if no canopy vanishes in `2` and no striking wrong textures appear, `KEEP_SHOWN=2` goes into the base profile;
- if it vanishes in `2` too, case 1 is next: following the draw command or instance count, with a logging measuring point written for it.
