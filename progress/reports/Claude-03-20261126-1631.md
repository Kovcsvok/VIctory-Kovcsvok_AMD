26 November 2026, 16:31 (local time). Previous: [Claude-02](Claude-02-20261126-1612.md).

## In short

1. **A0b ran for 13.1 minutes and did not crash.** The game exited normally (`title did not finish suspending in time; ending the title`). So A0's crash did not certainly come back. **Open question for the user:** did they load the 16:04 save and get past the point where A0 crashed (the robbery's `ROBBERY_FAIL` scene)? That decides whether the crash can be considered non-deterministic.
2. **Memory was even tighter than in A0.**
   - Lowest free commit 0.26 GiB, least free physical RAM 0.46 GiB.
   - The page file grew twice (16:24:19 and 16:25:58).
   - victory.exe's private memory was 29.5 GiB, shared GPU memory 10.9 GiB.
3. **In this run the stutters go together with low free commit.** With 1–2 GiB of free commit, 57% of the intervals had a frame of at least 250 ms; with 2–4 GiB, 19%. For frames over 500 ms the shares are 16.9% and 4.6%.
4. **`ab75ac3`'s targeted fault did not show this time either:** not one E_OUTOFMEMORY, `no upload buffer` or `no host texture` in the log.

Interpretation:
- The ≥ 4 GiB band is mostly the first minute after loading; the stutters there are mostly loading stutters.
- In A0b the long stutters are much more frequent in the stretches below 2 GiB.
- This is correlation, not a proven cause: heavy scenes may both eat memory and cause stutters.
- The B1 run with lower memory demand tests the causal link: the same scene and the same length, with the texture cap as the only difference.

## 3. The one suggested next experiment: B1, `-LowMemory` on the same stretch

- **Profile:** double-click `meresek\Meres-KLBF.cmd` → `2` (`-LowMemory`, 512 px) → Enter (name: `B1-rablas-512`). No new pre-building needed, because the texture cap is not part of the shader cache key.
- **Stretch:** the 16:04 autosave; the same robbery stretch, the same way, and get past A0's crash point.
- **Length:** 12 minutes from when the character can be controlled (the same as A0b's world stretch).
- **What I look at:**
  - how long free commit stays below 2 GiB;
  - how the share of ≥ 250 and ≥ 500 ms intervals changes;
  - the peaks of shared GPU memory and private memory;
  - whether the crash happens again;
  - and, from the user's notes, how much the picture gets worse.
- **If B1 has less time below 2 GiB and fewer long stutters,** the next development goal is cutting the main memory consumers: idle textures kept in VRAM (5.1 GB, no eviction happened; `VICTORY_TEXTURE_LRU`), GPU data overflowing into shared memory, and the page file. **If it does not drop,** memory is not why it stutters, and the loading and texture-queue path is next.
