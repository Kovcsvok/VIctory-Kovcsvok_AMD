## 2. Measurement: how much memory one command list takes on this card

**The test program:** our own, in the scratchpad (`allocmeres`); it does not touch the game. It measures how much memory a D3D12 command allocator with its list takes on the RX 9070 XT.

| Step | 500 lists | 100 lists |
|---|---|---|
| Created, empty | +549 MB private, **+500 MB shared** | +110 / +100 MB |
| 100 / 2,000 / 20,000 copies recorded per list | no growth | |
| 60,000 copies per list | | +212 / +200 MB |
| 200,000 copies per list | | +614 / **+600 MB** (6 MB per list) |
| Reset, then 1 copy | **kept** | **kept** (600 MB) |
| Allocator made again | | shared 103 MB, private stays 667 MB |
| All released | private +300 MB stays | private +376 MB stays |

**Conclusion:**
- On this driver **every list takes at least 1 MB** of shared RAM as soon as it is created.
- It grows in steps of a megabyte while recording, and does not give that back on reset.
- The driver keeps part of the released memory. So the answer is **fewer lists in the first place**, not releasing them afterwards.

**In the game:**
- **2,151 host lists** were alive;
- **1,909 of them also had a "prelude" list of their own** (with its own allocator);
- about 4,000 allocators in all, at least 4 GB, more with the bigger recordings.

## 3. Fix: a shared pool for the prelude lists (`VICTORY_PRELUDE_POOL=1`)

**What is a prelude?** A small list that runs a few state changes and texture copies before the main list.

**Until now:** every host list kept its own forever, even while it waited idle in the pool or for the game's next recording.

**Now:**
- Once all runs of a list have finished, its prelude goes into a shared pool of at most 192 (`crate::list::recycle` → `HostList::give_prelude`).
- The next list that needs a prelude takes one from there (`HostList::prelude`).
- The same safety condition as in the existing list pool: only preludes whose runs have finished go into the pool, and they are reset before use.

**Code changes** (`belobug-9070`, not committed):

| File | Change |
|---|---|
| `host.rs` | `prelude_pool()` (can also be switched with live A/B), `SPARE_PRELUDES` (at most 192), `give_prelude`, `spare_preludes`, `PRELUDE_POOL` counters |
| `list.rs` | `recycle` hands the prelude over. A new `VICTORY_LIST_IDLE_MOST` switch for the cap on idle lists (default 512, unchanged). It is not on in the menu: with 192 new lists had to be made more often. |
| `copystat.rs` | in the `memory, windows` log line: "preludes of the pool of spare ones: … taken, … given to it, … spare now" |

## 5. Measured but not yet fixed (next steps)

1. **Permanent host lists for the game's lists:** after every game list is submitted it gets a new, open host list right away, even if the game does not use it for a long time (about 1,900 alive). If it only got one at the game's next recording, it could be about 1–2 GB less. That is a bigger change in `list.rs`.
2. **Cached view shapes:** 1.5 million in 6 minutes. The cap is 4.2 million, about 1 GB. It can be lowered.
3. **`VICTORY_RESIDENCY=1`** (cool_fox): smaller frames on a 32 GB machine, and texture preloading limited below 3 GB of free RAM. But the hold-back drops from 64 submissions to 16, which caused the 11-25 device losses. Only worth trying together with `VICTORY_BURY_LAG=64`.
4. **Antigravity `efd3218`:** caps the pool of "thin" background lists at 64. By our log that is not the main item. The 32 GB texture-block cap is for shared-memory machines (our card has its own memory), so it does not help here.
