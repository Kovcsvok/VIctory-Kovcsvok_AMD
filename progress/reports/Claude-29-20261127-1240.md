## 3. The lost texture writes: the address is not in the view at all

The new build logged all 16 words of each lost writable view (75 lines, more than 16,384 lost writes by 11:25:29). Every one looks like this:

```
resource [3, 9, 0, 0, 1024, 0, 1024, 589825, 71, 1, 0, 261, 3145728, 32766]
view     [71, 4, 5768, 0, 0, 15, 0, 0, 0, 0, 0, 0, 0, 0, 0, 3]
```

- **Words 10–14 are 0 in every view, word 15 is always 3.** So the game passes no address when it creates these views, unlike its shader views (words 10–11).
- The views use the shader-view layout (`5768` = `0x1688`, the default component mapping, in word 2; the dimension in word 1 uses the shader-view numbering: 9 = cube).
- **Formats:** 71 BC1, 72 BC1 sRGB, 78 BC3 sRGB, 80 BC4, 98 BC7, 99 BC7 sRGB, and also 87 B8G8R8A8 (an uncompressed one, lost the same way); 4–1024 px, with mip chains; plain 2D textures and cube maps (`65542` = 6 faces).
- Layouts 261 and 266 (`0x105`, `0x10A`): the console's tiling modes.

**What this means:**
- The game creates the view without memory, and puts the address in later. Most likely it writes the address straight into the descriptor record in its heap: the log has many records "no store told of", found by port 2's fallback (`port_descriptors`), written by the game itself.
- So the fix cannot take the address from the creating call. It has to come from where the record is completed: the record the game writes, or the memory placement it uses for that texture.
- The block-twin plan (Claude-28, section 8) stays; only the way to find the texture changes. **Next step:** in `descriptor.rs` / `port_descriptors.rs`, follow a slot that got a placed writable view: what the game writes into that record afterwards, and whether the translator's own record for it is overwritten.

## 4. Why neither the CPU nor the GPU is full

**The HUD while sailing** (video 221–226 s): GPU 36–55% busy, CPU 47–66%, 14–20 fps, 53–73 ms a frame.

**The log, per frame, while sailing (11:24:4x–5x UTC):**

| What | ms per frame |
|---|---:|
| Frame time | 48–54 |
| **The submitting thread waiting for flights** (earlier submissions to finish on the card) | **20.1** |
| The list steps (refreshes, copies, fills) | 11.1 |
| The pass over the heap's views (slots 8.1, spans 3.1, textures 7.2; partly beside the recording) | ~18 |
| Asking the write watch | 3.6 |
| Snapshots | 3.5 |
| Copying back what shaders wrote | 8–13 |
| On the GPU | 18–25 |

**Why the 20 ms wait:** `card steps … 3.62 submissions waited for a learned page; 13 pages learned`. This is `CARD_STEPS_LEARN` (the boat fix): the game writes 13 memory pages (about 52 KB) after it submits, so every submission that fills from them waits until the card has finished everything before it. While the submitting thread waits, the card runs dry; while the thread then prepares, the card waits again. **The work is serialised, so neither side gets near 100%.** That is what the user sees as "the CPU is the bottleneck".

**The idea for the fix:** have the card read those 13 pages where the game writes them, at the moment it runs, as renderer port 1 already does for the game's 174 MB constants heap (a GPU-visible view of the game's memory). Then the fill gets the bytes the game wrote by then, as on the console, and nothing has to wait. If it works, sailing could go from about 20 fps to about 28–30 without losing the boat fix.

**Spikes:** the HUD shows frames of 65–125 ms (`MAX`) during sailing. The log only has 20 s averages; for spikes we need the per-frame times. The `frame account` and `A/B phase` lines exist; a per-frame log (frame time, waiting for flights, GPU time) is the first step, then the causes (pipeline making, texture uploads, page-ins) can be counted.
