# Antigravity's task for pre-building AGY v2

(A note by Codex.) 27 November 2026. The P1+P3+P4 build can be built and go to Claude. The pre-builder should get its own commit and an optional launcher. For a usable first version the two existing commands and exact accounting of the successful PSOs are enough.

1. Use the same AGY binary, working folder and renderer profile as the game. Check the host wave and view limit values too. By the local `victory.toml` the target folder is `VIctory-dev/state/agy-9070-v2/cache`. Print the resolved path and the build's identifier.
2. For the first run use the existing `victory translate --warm <list> --jobs 4` command on the game's shader sources. `AGY-eloforditas-shaderek.txt` holds 2,668 distinct identifiers of shaders actually bound in local Belobug play runs. The two finished runs alone cover the whole list. It is a starting list and can be extended with new identifiers from AGY runs. The number of identifiers not found among the sources should go into the report too. `VICTORY_WARM_SECONDS=90` is a soft budget for compiling; walking the archives and a compile in progress may take longer.
3. Turn on `VICTORY_PIPELINE_BOOK=1` in the AGY game profile. After the first normal play, use `victory warm --used --jobs 2` in the optional launcher. With an empty book it should say a play run is needed. The old Belobug cache has 3,609 distinct early pipeline keys, but at the check there was no `known-pipelines.bin` for them. The key list alone does not contain the data needed to rebuild. The current `warm` prepares the driver's cache.
4. Fix the completion accounting in AGY. `crates/victory-gpu/src/pipeline/known.rs` returns the result of creating the host pipeline. `apps/victory/src/warm.rs` counts the `there == false` case, but then writes the key into `warm-done.txt` all the same. A failed key should get a result of its own, and only PSOs actually created should go onto the done list. A regression test should show that the second run skips the successful key and does not treat the failed one as done. Think about migrating existing done lists when a cache already exists.
5. The report of the first and the repeated run should give the total wall-clock time, the memory peak, and the numbers of requested/found/new/already stored/failed items. In the next normal AGY run look at shader-cache misses, the long stutters in the first minute after loading and driver faults. In the 89+54 report windows of the earlier 22:47 and 20:51 runs the mean pipeline wait already rounded to 0.0 ms. That counter alone is too little to measure single spikes and time spent on other threads.

A full 20-thread compile, building every compute PSO cold, the 42 RT shaders and changing the in-game wait limits can be a separate experiment if the local measurement points there. `catch_unwind` protects against Rust panics; against driver crashes the relevant protection is a separate process. fxceless #1442 targets parallelising library loads of different keys. The save stutter needs a separate measurement. [Upstream PR](https://github.com/fxceless/victory-fork/pull/1442)
