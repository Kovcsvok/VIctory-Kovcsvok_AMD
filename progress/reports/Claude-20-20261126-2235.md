**What happens in the code** (`crates/victory-gpu/src/port_descriptors.rs`, header):

1. The game fills the draws' descriptor tables in its own frame allocator, 32 bytes a record.
2. Port 2 patches six store instructions: they report which record changed, and the program copies only those into its own descriptor table.
3. **What no patch reports is only found by the fallback search.** That looks at only 16 changed pages a frame (`check_budget`, default 16 pages, `check_every` 8).
4. Until then the old descriptor stays in the record's place. A tree whose table has such a record (an instance-data buffer, a texture) reads wrong or empty data in that frame.

**By the 21:21:10 summary there had been 765,003 unreported view records since the start.** Their writers:

| Writer | Records |
|---|---|
| `0x7fff61eccd9f` (not the game's: a system DLL memcpy) | 267,705 |
| `title+0x18849c` | 178,241 |
| `0x7ffea5920000` (not the game's) | 85,357 |
| `title+0x4e9b4e2` | 59,168 |
| `0x7fff61eccd03` (not the game's) | 42,557 |
| `title+0x2474afc` | 30,762 |

- Of the game's memcpy/memmove calls, about 3,400 a frame write into the table, but none marks anything ("0 records they marked").
- avatarmanz's `VICTORY_PORT_COPIES` hook catches the game's own table copier (+0x4d9f26e/+0x4d9f386/+0x4d9f54c), but not the system DLL's memcpy or `title+0x18849c`.

**Compared across runs** (number of warning lines):

- Without port 2 the program works the old way: every frame it scans all changed pages of the table (~290 pages, ~600,000 records), so no record can be missed.

## 3. The video (22:21, without port 1, camera still)

The flash finder ran on all 581 frames (threshold 10):
- **19 frames with a flash, 16 of them in the same place:** at the left edge, in the line of trees on the horizon, about 0.8 a second over 19.4 s.
- So the user's "consistent spot" is measurable. I will compare the option-`8` run's video by the same number.

**What flashes?** At 4.47 s and 15.97 s (full-resolution crops `Port1ki-4s47-fasor-lod-villan.jpg` and `Port1ki-15s97-fasor-lod-villan.jpg`, local only):
- for one frame the leftmost palm vanishes, and a palm appears elsewhere;
- the canopies behind it are drawn with a dotted, broken pattern;
- the next frame everything is back.

The dotted pattern is typical of the cross-fade (dither) between levels of detail. In that frame the trees get wrong LOD or cross-fade data. That fits port 2's missing reports: a record not refreshed in the frame allocator's tables points to an earlier frame's data. This is not proof yet; the option-`8` run decides.

*(Later, Claude-21: the real cause was null twin views in the tree culling pass; fixed with `VICTORY_TWIN_MOVE`.)*
