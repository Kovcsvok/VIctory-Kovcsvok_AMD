# Claude-02 · A0 cold baseline run: crash in the prologue's robbery scene

26 November 2026, 16:12 (local time). Previous: [Claude-01](Claude-01-20261126-1548.md).

## In short

1. **The A0 run crashed after 8 minutes 32 seconds of play.** The translated game code read a null pointer: `0xc0000005` at `victory-image-b99f876b74d4a77f.dll+0x6c0524` (`read 0x30: nothing mapped there`). According to the game's own crash log it was preloading one of the cutscenes of the prologue's robbery scene: `int_prolo_INT_PROLO_MCS6_ROBBERY_FAIL_min`, state `Prestream`.
2. **Windows commit was tight for most of the run.** It stayed below 4 GiB for 75% of the time in the world (from 16:04:13). At 16:09:15 it fell to 0.51 GiB, after which the system grew the page file by 1 GiB (16:09:16). At the moment of the crash (16:09:31) free commit was 2.2 GiB.
3. **The fault `ab75ac3` fixes did not appear.** There was no `no upload buffer`, no `no host texture`, no `0x8007000E`. So the verdict: **`ab75ac3` is not the right next step for this run** (reasons in section 4).
4. **The first fault is now the crash.** By the test plan it has to be repeated once with the same settings first. That shows whether a deterministic emulation fault or memory shortage causes it.

## 4. What does this mean for `ab75ac3`?

- **The targeted fault did not occur.** The system refused no GPU memory allocation, so parts A, B and D of `ab75ac3` (Claude-01, section 3) would not have acted in this run.
- **The commit gate (part C) would turn on below 4 GiB, which is 75% of the world time here.** It would then hold back uploads of textures picked by index, although the queue already grew to 16,372 slots without it. It would not help the main commit consumers: shared GPU memory (8.6–9.7 GiB), host copies of game memory (4.1 GiB) and windows (3.6 GiB) would stay untouched. It would probably bring more late textures and free little memory.
- **The decision rule suggested in Claude-01 was met to the letter** (in 19 of the 25 worst stutters free commit was below 4 GiB). But the new data shows two things: `ab75ac3`'s targeted fault did not appear, and there is an earlier, more serious fault, the crash. So I ask for the rule to change (section 6).

## 5. The crash

- KLBF log: `meresek\20261126-160059-A0-prologus-hideg\crashes.log` (a copy of `VIctory-dev\state\klbf-lab\data\7952987A\crashes.log`).
- The game's own crash log: `VIctory-dev\state\klbf-lab\data\7952987A\temp\victory-20261126-160933-15972.crash.log`, minidump: `…\temp\00000000-0000-0000-0000-000000000000.dmp` (37.8 MB). The game tried to upload the crash report, but KLBF blocked it (`HTTP connection blocked destination=submit.backtrace.io:443`).
- Call chain: `victory-image…+0x6c0524` ← `+0x6c01e0` ← `+0x259105d` ← `+0x2592d0f` ← `+0x2215eca` ← `KERNEL32` ← `ntdll`. Among the registers `rdx = rdi = 0`; a read of null pointer + 0x30.
- **Two possible explanations:**
  - **A deterministic emulation fault** in preloading `ROBBERY_FAIL`.
  - **A refused memory allocation** in game memory: KLBF's `XMemVirtualAlloc` (`crates/victory-hle/src/modules/xmem.rs` 87) returns a null pointer without logging when it fails, so the log cannot rule this out.
- The timing favours the second (16 s after the commit minimum, during a loading wave). But at the crash 2.2 GiB of commit was free, so one run cannot decide.

## 6. The one suggested next experiment: A0b, a repeat with the same settings

1. Start with the same default setting: double-click `meresek\Meres-KLBF.cmd`, name `A0b-rablas-ismetles`. The same programs should run in the background as now.
2. From the **Load** menu load the 16:04 autosave (if it shows up), and play through the robbery the same way as now.
3. Evaluation:
   - **If it crashes at the same address** (`+0x6c0524`) **and in the same scene** (preloading `ROBBERY_FAIL`), it is a deterministic fault. That becomes the first fault to fix; by the test plan it should also be tried with the United launcher.
   - **If elsewhere, or no crash,** memory shortage is more likely. Then the `-LowMemory` run and cutting memory consumers come next: idle but kept textures (5.1 GB), `VICTORY_TEXTURE_LRU`, the page file.

Reason: by the test plan the first repeatable fault comes before performance work. The same repeat also shows whether the crash depends on memory.
