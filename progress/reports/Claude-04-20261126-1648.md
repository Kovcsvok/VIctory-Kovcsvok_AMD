# Claude-04 · B1 (`-LowMemory`): fewer long stutters, but a GPU hang in the car chase

26 November 2026, 16:48 (local time). Previous: [Claude-03](Claude-03-20261126-1631.md).

## In short

1. **B1 stopped in its 9.3rd minute in the world; according to the user, during the car chase.**
   - The GPU stopped responding, and Windows removed it: `DXGI_ERROR_DEVICE_HUNG` (0x887A0006), 16:45:35.
   - This is a different fault from A0's null-pointer read in the game's code.
   - GPU debugging breadcrumbs (DRED) are not available for this device (0x887A0004), so the log does not name the faulting GPU command.
2. **A0's crash is probably not deterministic.** The car chase comes after the robbery, so B1 got past the point where A0 crashed (to be confirmed by the user).
3. **`-LowMemory` visibly reduced the long stutters.** Comparing the world's first 10 minutes with A0b:
   - frames of at least 500 ms in 1.5% of intervals instead of 8.2%;
   - frames of at least 1 s: 1 instead of 12;
   - the mean frame time did not change (73.4 and 74.4 ms).
4. **The memory ceiling did not go away.**
   - The share of time with less than 4 GiB of free commit fell from 94% to 44%, but the share below 2 GiB stayed at 31%, with a minimum of 0.32 GiB.
   - At the stop there were 1.65 GiB of free commit and 1.05 GiB of free RAM.
5. **Pattern:** two of three runs crashed after 8.5–9.5 minutes of world time, both with memory exhausted, with two different faults. The common factor is memory shortage, but that is not a proven cause yet.
6. **`ab75ac3`'s targeted fault was missing in all three runs:** not one E_OUTOFMEMORY, `no upload buffer` or `no host texture`.

*(Later, Claude-05: B2 did not repeat the stutter reduction, so that claim was withdrawn.)*

## 2. B1's stop

- KLBF log (`victory.log`, 15:45:35 UTC):
  - `host GPU device removed after 2 submissions sent ahead … device removed: … (0x887A0006)`
  - `when the host device went: the submitting thread was preparing a submission (nothing of ours was running on the card)`
  - Right before it came 16 `no shared buffer … (0x887A0005)` lines: already consequences of the removed device.
- In the last second new pipelines were bound for the first time (`first bind … frame=8624/8625`), which points to a scene change.
- In the copy of `crashes.log` the first entry was still A0's. I fixed the launcher: from now on only the run's own new entries go into its folder (the cutting logic tested).
- **Windows background.** Between 16:45:38 and 41 the error reporter sent the queued old reports all at once: LiveKernelEvent 141/117 (GPU timeout), 124 (WHEA) and two 0x7E blue screens. The System log has 28 WHEA hardware events between 5 and 20 November, none today. CPU microcode 0x133 (from the registry), BIOS E2.6D (2026-03-11). The machine's earlier stability history is a confounding factor to keep in mind.

## 3. The one suggested next experiment: B2, B1's settings + a larger, fixed page file

**The only difference from B1 is the commit reserve.** The limit is currently 51.85 GiB (a system-managed 20 GiB page file that only grows when it runs out). Drive C: has 228 GB free.

What the user does (a system setting, can be reverted any time):

1. `Win + R` → `SystemPropertiesPerformance` → **Advanced** tab → Virtual memory: **Change…**
2. Turn off "Automatically manage paging file size for all drives".
3. Select drive C: → **Custom size**: initial 40960 MB, maximum 65536 MB → **Set** → OK.
4. Restart the machine.
5. Then double-click `meresek\Meres-KLBF.cmd`, profile `2`, name `B2-lapozo-512`. From the same 16:04 save, the same way, and **get past the car chase**. Play for 12 minutes.

To revert: turn automatic management back on in the same place.

**Evaluation:**
- **If B2 gets past the chase and free commit stays above 4 GiB throughout,** the crashes are probably caused by commit running out. Then the development goal is lowering peak memory:
  - `play.ps1`'s large reserves: `VICTORY_STAGE_POOL_MB=2048`, `VICTORY_LIST_POOL_MB=2048`, `VICTORY_CARD_WINDOWS_MB=4096`;
  - idle textures kept in VRAM (5.1 GB);
  - data overflowing into shared GPU memory.
  - The page-file advice goes into the guide.
- **If it stops even with enough commit,** the stop does not depend on commit. Then the GPU hang is investigated further with the debug build (`VICTORY_D3D12_DEBUG=1`), and A0's null pointer with the minidump.
